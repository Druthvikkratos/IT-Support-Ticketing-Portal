## 📖 What is InfoDesk?

InfoDesk is a ticketing system built for a single IT team supporting a company of employees. Instead of "someone post it in a group chat and hope IT notices," employees raise structured tickets, optionally get **instant self-service guidance from a rule-based bot**, chat live with whichever admin picks up their case, and get notified the moment anything changes — all from one portal.

It was built end-to-end: schema design, authentication, dynamic form configuration, file validation, WebSocket chat, notifications, dashboards, and reporting — with an emphasis on **audit trails** (nothing is ever silently deleted or changed without a trace) and **role-correct access** (an employee can never see another employee's ticket; an admin can't touch a ticket another admin has claimed).

## ✨ What it offers

### For Employees
- 🎫 **Raise tickets** through an admin-configurable dynamic form — text, dropdowns, checkboxes, file uploads, and more, all defined without touching code
- 🤖 **Instant bot guidance** — common issues (configured per issue type) get step-by-step self-help instructions before ever reaching a human
- 💬 **Live chat** with the admin handling their ticket, with typing indicators and online/last-seen presence
- 🔔 **Real-time notifications** for status changes, replies, and resolutions
- 📎 **Attach screenshots, PDFs, and Excel files** — validated by actual file content, not just the extension
- 📊 **Personal dashboard** showing their own ticket status at a glance
- 🔑 **Self-service password reset** (identity verified via employee code + registered email — no "forgot password" email dependency)
- 📡 **Offline-first submission** — if the network drops, tickets queue on-device and send automatically once connectivity returns
- 🌓 Clean, responsive UI with light/dark considerations

### For Admins
- 🏷️ **Claim / reassign tickets** — once claimed, a ticket is locked to that admin until they hand it off, with a full assignment audit trail
- 🛠️ **Form Builder** — build the employee ticket form visually: add fields, reorder by drag-and-drop, configure file-upload constraints (type, size, multiplicity) per field
- 🤖 **Bot Guide editor** — write the self-service steps the bot offers per issue type
- 👥 **User management** — create/edit/deactivate admins and employees, **bulk-upload employees via Excel** with a detailed pass/fail results report
- 📈 **Live dashboard** — status breakdown, a 14-day ticket trend chart, and a pulsing real-time activity feed
- 🕵️ **Global History** — a searchable, filterable audit log across every ticket's status changes and messages
- 📑 **Excel reports** — generate a full ticket export for any date range, styled and ready to share
- ⏱️ **SLA / overdue flags** — tickets open too long for their priority are flagged automatically
- 🔐 Rate-limited login, short session windows, and strict role separation throughout

## 🧱 Tech Stack

| Layer | Technology | Why |
|---|---|---|
| Backend framework | **NestJS** (TypeScript) | Structured, testable, dependency-injected — scales well past a single script |
| Database | **MySQL** | Reliable, widely supported, pairs cleanly with Prisma |
| ORM | **Prisma** | Type-safe queries, clean migration history, autogenerated client |
| Auth | **JWT in httpOnly cookies** | No token exposure to JS — mitigates XSS token theft |
| Real-time | **Socket.IO** (NestJS Gateways) | Chat, typing indicators, and live presence over a single persistent connection |
| File handling | **Multer** + **file-type** (magic-byte sniffing) | Uploads are validated by real binary content, not filename/MIME claims |
| Reporting | **ExcelJS** | Styled, formula-safe `.xlsx` generation for reports and bulk-upload results |
| Rate limiting | **@nestjs/throttler** | Protects login and AI endpoints from abuse |
| Frontend framework | **Angular** (standalone components, Signals) | Modern reactive state without NgRx overhead |
| Styling | **Bootstrap 5** + custom SCSS | Fast, consistent, themeable |
| Icons | **Tabler Icons** | Clean, consistent icon set |
| Alerts/modals | **SweetAlert2** | Accessible, non-blocking confirmation flows |
| Charts | **Chart.js** | Dashboard trend visualization |
| Offline support | **Angular Service Worker** + **IndexedDB** (`idb-keyval`) | App-shell caching and an offline ticket "outbox" that syncs on reconnect |
| AI (optional) | **Ollama** (local LLM) | Free, local ticket-field suggestions and chat summarization — no cloud dependency |

## 🏗️ Architecture at a glance

```
infodesk/
├── backend/                  NestJS API
│   ├── prisma/
│   │   ├── schema.prisma     Single source of truth for the DB
│   │   ├── migrations/       Versioned, incremental schema history
│   │   └── seed.ts           Default admin, issue types, ticket counter
│   ├── assets/                Uploaded files (gitignored — never committed)
│   └── src/
│       ├── modules/           auth, users, tickets, chat, notifications,
│       │                      dashboard, reports, history, bot, ai, settings...
│       └── common/             guards, decorators, shared utils
│
└── frontend/                  Angular app
    └── src/app/
        ├── core/               services, models, guards, interceptors
        ├── layout/             shell, sidebar, topbar
        ├── features/           one folder per screen/module
        └── shared/             reusable pipes & styles
```

Every feature follows the same pattern end to end: **Prisma model → DTO validation → Service (business logic + logging) → Controller (route + guards) → Angular service → Component**. Role checks happen in two layers — route-level guards (`@Roles('admin')`) for "what kind of user is this," and service-level ownership checks for "does this user own *this specific record*."

## 🚀 Running Locally

### Prerequisites
- Node.js 18+
- MySQL 8+ running locally
- (Optional) [Ollama](https://ollama.com) installed if you want the AI features

### 1. Clone & install
```bash
git clone <your-repo-url> infodesk
cd infodesk/backend && npm install
cd ../frontend && npm install
```

### 2. Configure environment

`backend/.env`:
```env
DATABASE_URL="mysql://root:yourpassword@localhost:3306/infodesk"
JWT_SECRET="replace-with-a-long-random-string"
JWT_EXPIRY=10h
FRONTEND_URL=http://localhost:4200
THROTTLE_TTL=60
THROTTLE_LIMIT=20
OLLAMA_URL=http://localhost:11434
OLLAMA_MODEL=llama3.2:3b
```

`frontend/src/environments/environment.ts` is already configured to derive the API host from the browser's own URL (`window.location.hostname`), so it works unmodified on `localhost` or a LAN IP.

### 3. Database — pick ONE path depending on what you have

#### ✅ Path A — Migration history is present (`backend/prisma/migrations/` exists and has folders in it)

This is the normal path for anyone cloning the repo as-is.

```bash
cd backend
npx prisma generate          # generate the typed Prisma client
npx prisma migrate dev       # apply all existing migrations to your local DB
npx prisma db seed           # creates the default admin + seed data
```

#### ⚠️ Path B — No migrations present (folder missing, empty, or you want a completely fresh schema)

This happens if migrations were intentionally wiped (e.g. during schema cleanup) or you're setting up a brand-new environment from `schema.prisma` alone.

```bash
cd backend

# 1. Make sure the target database exists and is empty
mysql -u root -p -e "DROP DATABASE IF EXISTS infodesk; CREATE DATABASE infodesk;"

# 2. Generate ONE fresh initial migration from the current schema.prisma
npx prisma migrate dev --name init

# 3. Generate the Prisma client
npx prisma generate

# 4. Seed default data (default admin, issue types, ticket counter row)
npx prisma db seed
```

> **Never run `prisma migrate dev` against a production database** — it's a development-only command and can prompt destructive resets. Production deploys use `npx prisma migrate deploy`, which only applies existing migration files and never generates new ones or resets data.

### 4. Run both apps
```bash
# backend
cd backend && npm run start:dev    # http://localhost:3000

# frontend (separate terminal)
cd frontend && ng serve            # http://localhost:4200
```

### 5. First login
The seed script creates a default admin:
```
Email:    admin@infomapglobal.com
Password: (set in your seed script / .env — change it immediately after first login)
```

### 6. (Optional) AI features
```bash
ollama pull llama3.2:3b
ollama serve   # usually starts automatically after install
```
If Ollama isn't running, AI-powered buttons degrade gracefully with a friendly "unavailable" message — the rest of the app is unaffected.

## 🧪 Resetting the database during development

If you need a clean slate while iterating on the schema locally:
```bash
npx prisma migrate reset
```
This drops the database, reapplies every migration from scratch, and reruns the seed — all in one command. Development only.

## 📦 Deploying

```bash
npm ci
npx prisma generate
npx prisma migrate deploy   # applies committed migrations only — never resets data
npx prisma db seed          # safe to rerun — uses upsert/existence checks
npm run build
```
Put the app behind HTTPS (required for the service worker and secure cookies) and set `app.set('trust proxy', 1)` in `main.ts` if running behind a load balancer or reverse proxy.

## 🗺️ Key design decisions

- **Soft deletes everywhere, except one explicit exception.** Users, issue types, and form fields are deactivated, never hard-deleted — history and tickets referencing them stay intact. The one deliberate exception: an admin can **permanently** delete an employee's entire footprint (tickets, chat, attachments, notifications) for offboarding, gated behind a type-to-confirm safeguard.
- **Atomic ticket numbering.** `INFO-0001`-style numbers are generated via a single-row counter table incremented inside a database transaction, so concurrent submissions can never collide.
- **Magic-byte file validation.** Every upload is checked against its *actual* binary signature, not its extension or claimed MIME type — a renamed `.exe` disguised as a `.pdf` is rejected at the content level.
- **Assignment locking.** Only the admin who claimed a ticket can change its status, preventing two admins from working the same case at once.
- **Offline-first ticket submission.** Tickets are queued client-side with an idempotency key when the server is unreachable, so retried/duplicate submissions never create duplicate tickets once connectivity returns.
